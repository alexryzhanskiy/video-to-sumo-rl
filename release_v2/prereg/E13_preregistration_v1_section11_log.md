## Deviations

All of the following were found while building and testing the E13 kit on 29 Oct 2026, **before any E13 training or evaluation run**. Build: `revision/tools/build_e13_kit.py`. Tests: `revision/tools/test_e13_kit.py`, `revision/e12_kit/e13/runs_test/test_report.json`.

| # | Type | Entry |
|---|---|---|
| D1 | Bug fix (known issue K32) | MPLight's phase input in this RESCO fork is `raw_phase // 2`, written for a program with two green phases. With this junction's four green phases, it reports phase 0 (Svobody through) while Svobody through or left is green, and phase 1 (Svobody left) while a Prybuzka phase is green. The FRAP model therefore never sees the correct green phase. E13 runs MPLight with `--mplight_phase fixed` (the green-phase index 0–3). The original and E12 MPLight results used the faulty input. The L0 re-evaluation keeps it (`legacy`) so that it reproduces E12. |
| D2 | Architecture | MPLight's FRAP model takes only the green-phase index and the per-movement demands. Adding the elapsed green time would need a change to its architecture. In E13, MPLight therefore gets the green limits through action masking only. The three IDQN variants get the extra input row (elapsed green / 60 s and the green-phase one-hot), as pre-registered. |
| D3 | Implementation of L2 | The "extend or go to the next phase" choice of L2 is implemented by masking the 4-phase output to {current phase, next phase in field order}. IDQN and MPLight thus keep their network outputs, and the choice set is the pre-registered one. |
| D4 | Clarification | Epsilon decays linearly over the first 80% of the training steps, as in E12 (`main.py`: `episodes = int(eps * 0.8)`). Section 2 says "over all training steps"; nothing changes from E12. |
| D5 | Implementation detail | Masking applies to action selection: greedy and random choices are made among legal actions only. The DQN target keeps pfrl's maximum over all actions, as RESCO's own `valid_acts` code does. |
| D6 | Clarification | With 5-s decisions, a green lasts 2 + 5k s at each decision, so the longest green is 57 s (forced change). This satisfies the 60-s maximum. The tests found greens of 12–57 s. |
| D7 | Implementation detail | The L4 mix map holds all 60 mix files in one fixed order: a NumPy `default_rng(6100)` permutation, recorded in `environments/prybuzka_mix/route_order.txt`. RESCO then cycles through them, so 300 episodes see each file 5 times. Section 3 does not specify the order; a shuffle avoids a systematic sweep from low to high load. |
| D8 | Demand generation notes | Demand sets in `revision/demand/e13/` (README there). Counts: 38 validation files (10 per load + 2 per scenario), 50 locked-test files (10 per load + 5 per scenario) and 60 mix files. The loads ×0.8, ×1.4 and ×1.6 use the rule recovered from the ×1.2 and ×1.5 files: each cell × factor, rounded half to even. The mix parameters were drawn with `default_rng(6000)` before generation (`mix/mix_params.json`). Sanity flags were recorded and **no file was dropped**, as pre-registered: the fixed plan is flagged on validation ×1.5 10/10 (as accepted for ×1.5 in P01) and on 27 of the 60 mix files (×1.4, ×1.6 and 15 perturbed files). The locked-test files were never simulated; `revision/prereg/locked_test_hashes.txt` lists 72 SHA-256 values and verifies. Five route files (four new, one E12 training file) have one vehicle departing exactly at an interval end; this is a routeSampler rounding artefact, and the files are kept. |
